Módulo 1 — Fundamentos da Arquitetura de Dados

TEORIA

1.1 Explicação

Arquitetura de Dados é o conjunto de princípios, práticas e tecnologias que define como os dados fluem no âmbito de uma organização — da coleta ao consumo. Metaforicamente, equivale à "planta da residência": sem ela, cada instrumento opera de modo isolado; com ela, tudo se interconecta.

Por que importa

Dispor de dados não é suficiente: organizações que estruturam bem seus dados decidem melhor. Uma arquitetura consistente equilibra três dimensões, que se influenciam reciprocamente: técnica (a ferramenta adequada), organizacional (a repartição de responsabilidades) e regulatória (o que é permitido, ex.: LGPD).

1.2 Conceitos-chave

ConceitoSignificado
Metadados"dados sobre dados": origem, formato, qualidade, relacionamentos.
Data Lineagerastrear de onde veio e por onde passou um dado.
Data Fabricintegrar dados distribuídos com acesso unificado, independente da localização.
Data Meshtratar domínios de dados como produtos, com responsabilidade descentralizada.
Latênciatempo entre o dado ser criado e estar disponível — influencia a arquitetura.

1.3 Fundamentação teórica — tipos de dados

É recorrente o equívoco de tratar todos os dados como equivalentes. Cada categoria impõe requisitos distintos de armazenamento, processamento e governança.

Integrar todos esses tipos de forma eficiente é um dos maiores desafios da área. É exatamente isso que as arquiteturas dos módulos seguintes tentam resolver.

Módulo 2 — Modelagem de dados

TEORIA

2.1 Explicação

Modelagem de dados é o processo de traduzir requisitos de negócio em estruturas de dados. Corresponde ao "projeto" antes da "obra": na ausência de um modelo adequado, o banco torna-se confuso e lento.

2.2 Fundamentação — os três níveis de abstração

NívelO que fazPensa em
Conceitualentidades, relações e regras de negócio, em alto nível.o que existe no mundo (independente de tecnologia)
Lógicoestrutura detalhada, tabelas, chaves, mas ainda sem detalhes de gravação.como organizar os dados
Físicocomo os dados são efetivamente armazenados (índices, tipos, particionamento).performance e armazenamento
A progressão lógica

Recomenda-se iniciar pelo conceitual (o que importa), prosseguir ao lógico (a estrutura) e concluir no físico (a otimização). Ignorar o conceitual, visando acelerar a execução, é a origem de bancos mal estruturados.

2.3 Prática — modelo dimensional

Para fins analíticos, o modelo mais empregado é o dimensional, com os esquemas:

  • Star schema — uma tabela de fatos (eventos) circundada por tabelas de dimensões (contexto).
  • Snowflake schema — dimensões normalizadas em um conjunto maior de tabelas.
Aplicação

Esse modelo é o núcleo dos data warehouses: fatos = valores que se pretende somar (vendas); dimensões = critérios de segmentação (tempo, região, produto). É o que viabiliza, por exemplo, "vendas por região no mês corrente".

Módulo 3 — As arquiteturas: do warehouse ao mesh

PRÁTICA

Esta é, porventura, a parte de maior interesse: compreender os modelos arquiteturais e suas respectivas aplicações.

1. Data Warehouse (DW) — o tradicional
Consolidado nos anos 1990. Repositório central, otimizado para análise. Bill Inmon o define como "coleção de dados orientada a assuntos, integrada, não volátil e variante no tempo".
Prós: relatórios consistentes e confiáveis. Contras: rígido e caro para dados não estruturados. Padrão: ETL em lote, modelo dimensional.
2. Data Lake — o bruto e flexível
Com o Big Data. Guarda dados brutos (sem transformar antes) pelo princípio schema-on-read.
Prós: qualquer formato, barato, escalável. Contras: sem estrutura, vira "pântano" (data swamp) sem governança. Padrão: ELT, transformação tardia.
3. Lakehouse — o melhor dos dois
O híbrido moderno. Junta a flexibilidade do lake com a estrutura e transações do warehouse, usando tecnologias como Delta Lake, Iceberg, Hudi sobre armazenamento de objetos.
Uso: é hoje o ponto de partida de muitas organizações.
4. Data Mesh — o descentralizado
Criado por Zhamak Dehghani. Trata dados como produtos, com a propriedade descentralizada por domínio. Quatro princípios: propriedade por domínio, dados como produto, plataforma self-service e governança federada.
5. Data Fabric — o integrador inteligente
Integra fontes heterogêneas distribuídas com metadados ativos e automação/IA. Dá acesso unificado independente de onde os dados estão.
6. Arquitetura orientada a eventos (Event-Driven)
O evento é a unidade principal. Usa brokers (ex.: Kafka) e streaming. Uso: detecção de fraude, monitoramento IoT, personalização em tempo real.
7. Arquitetura Lambda
De Nathan Marz. Combina batch e streaming: uma camada batch (histórico), uma speed (tempo real) e uma serving (consolida).
Como escolher
Sua necessidadeArquitetura
Relatórios consistentes e corporativosWarehouse

Módulo 4 — Governança e qualidade de dados

PRÁTICA

Arquitetura destituída de governança assemelha-se a uma residência sem normas de convivência: funciona, porém rapidamente se deteriora. É nesse âmbito que se define quem responde pelos dados.

Papéis-chave
PapelResponsabilidade
Data Ownerresponde pelo dado e decide sobre ele.
Data Stewardresponsável pela qualidade e pelo uso quotidiano.
Data Custodianresponsável pelo aspecto técnico (armazenamento, segurança).

4.1 Qualidade de dados

Uma governança adequada assegura dados de qualidade, avaliada por dimensões como:

  • Precisão — o valor está correto?
  • Completude — há lacunas de informação?
  • Consistência — a mesma informação é registrada sempre da mesma forma?
  • Atualidade — corresponde ao momento vigente?
  • Unicidade — inexistem duplicidades?

4.2 Segurança e privacidade

O que a arquitetura deve assegurar
  • Controle de acesso — definição de quem pode visualizar cada dado (permissões).
  • Privacidade — conformidade com a LGPD e a GDPR.
  • Rastreabilidade — data lineage para auditar a origem de cada dado.
  • Metadados ativos — catálogo que viabiliza a descoberta do que existe.
A regra prática

Escalabilidade e desempenho só se mostram sustentáveis com governança mínima de qualidade e segurança. Um data lake desprovido de catálogo e permissões converte-se em "pântano" — e ninguém lhe confere credibilidade.

Módulo 5 — Por onde começar

ROTEIRO

Não é necessário projetar a arquitetura de uma organização inteira; basta começar pelo essencial.

1
Entenda os tipos de dados disponíveis Estruturados? Não estruturados? Em grande ou pequena quantidade? Essa avaliação condiciona todas as etapas subsequentes.
2
Modele o que importa Elabore o modelo conceitual do seu domínio (entidades e relações).
3
Escolha uma arquitetura Para iniciar: um warehouse (se o foco é relatório) ou um lakehouse (se é análise + machine learning).
4
Documente os metadados Registre a origem e a nomenclatura dos dados — o mínimo necessário para evitar a desorganização.
5
Considere a segurança desde o início Defina as permissões de acesso e observe a LGPD e a GDPR.

5.1 Primeiro exercício prático

CÓDIGO — modelo dimensional simples em SQL
CREATE TABLE dim_tempo (id_tempo INT PRIMARY KEY, ano INT, mes INT);
CREATE TABLE dim_regiao (id_regiao INT PRIMARY KEY, nome_regiao TEXT);
CREATE TABLE fato_vendas (id INT PRIMARY KEY,
                      id_tempo INT, id_regiao INT, valor NUMERIC);
Fato (vendas) + dimensões (tempo, região) = o modelo que sustenta as análises.

5.2 Checklist

  • Diferencio os tipos de dados
  • Conheço os 3 níveis de modelagem (conceitual, lógico, físico)
  • Reconheço warehouse, lake, lakehouse e mesh
  • Compreendo metadados e data lineage
  • Entendo os papéis de owner, steward e custodian
  • Sei por que a governança evita o "pântano de dados"
Consideração final

Estrutura não é burocracia — é o que propicia velocidade com confiança. Recomenda-se começar de forma simples, documentar os metadados, eleger uma arquitetura coerente com o objetivo e crescer progressivamente. Uma boa planta concebida hoje evita a reforma de amanhã.
